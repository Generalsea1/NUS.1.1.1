# NUS — Smart Shopping Architecture

## Scope

Phase 6.4.2 establishes the Smart Shopping domain and local persistence foundation only. UI, lifecycle/application services, reminders, cloud sync, financial integration, AI, family sharing, retailer integrations, product catalogs, pricing, inventory, and barcode/OCR features remain outside this phase.

## Aggregate boundary

`ShoppingList` is the aggregate root. It owns an ordered collection of `ShoppingItem` children. `ShoppingItem` has no independent repository boundary.

```text
ShoppingList
    └── ShoppingItem[]
```

## Domain model

`ShoppingList` contains:

- stable opaque `id`
- trimmed non-empty `name`
- owned ordered `items`

`ShoppingItem` contains:

- stable opaque `id`
- trimmed non-empty `name`
- optional `quantity` stored as user text
- deterministic `isCompleted` state

Quantity is deliberately not numeric and has no unit-conversion semantics.

## Aggregate invariants

The aggregate rejects duplicate child IDs, malformed children, empty IDs, and empty names. Its item collection is defensively exposed as an unmodifiable list. Add, update, remove, set-completed, and toggle operations preserve child identity and aggregate invariants.

Adding a duplicate item ID or updating/completing a missing item is rejected. Removing a missing item is a deterministic no-op.

## Identity

IDs are opaque stable strings supplied/generated by the application boundary. IDs are independent of user-entered names, list indexes, hash codes, quantities, and other content. Renaming a list or item never changes its ID. IDs survive repository reload.

No UUID or other new dependency is required by this phase.

## Serialization

The domain uses explicit deterministic JSON fields:

```json
{
  "id": "...",
  "name": "...",
  "items": [
    {
      "id": "...",
      "name": "...",
      "quantity": "...",
      "isCompleted": false
    }
  ]
}
```

No Flutter objects, runtime-only fields, enum indexes, or storage references appear in the domain model.

## Defensive persistence

`LocalShoppingRepository` implements `ShoppingRepository<ShoppingList>` using `SharedPreferences` with the dedicated key `nus.shopping.v1`.

Malformed root JSON returns an empty collection. Malformed individual aggregate records are ignored so valid lists remain loadable. Duplicate persisted list IDs are de-duplicated on read, with the first valid record retained. Saving an existing list ID replaces that aggregate instead of appending a duplicate.

Repository output is deterministic by `ShoppingList.id`. Item order is the aggregate's logical order and is preserved through serialization/reload.

## Repository boundary

The repository exposes only aggregate-level operations from the shared `DomainRepository` contract:

- `getById`
- `list`
- `save`
- `deleteById`

There is no `ShoppingItem` repository and no search, store, price, purchase, product, or inventory persistence boundary in this phase.

## Storage isolation

Smart Shopping uses only `nus.shopping.v1`. It does not modify `nus.schedule.v1`, `nus.appointments.v1`, or `nus.medications.v1`.

## Privacy

IDs and logs must not contain user-entered shopping content or derived sensitive information. In particular, item names, list names, quantities, notes, prices, personal information, and future external product identifiers must never be embedded in IDs.

## Future boundaries

Future Shopping capabilities may be added behind new application/data boundaries, but the current domain remains independent of Expenses, Budget, Bills, Notes, Home Manager, AI, Family Mode, Supabase, reminders, and external retailer/product services.
